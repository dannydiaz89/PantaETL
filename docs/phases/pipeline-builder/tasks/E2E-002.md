## Notes / blockers

The web application had no way to know whether a pipeline had a real active or queued
run: the execution-state helper always reported no active run, so a pipeline could
never actually become non-editable. Added a real read path (an owner-scoped active-run
query, a new execution-state endpoint and contract, and a query wired into the pipeline
workspace) so the editor genuinely locks once a run is queued or active.

The browser suite's `webServer` now also starts the scheduler service (on
`PLAYWRIGHT_PORT + 10`) so "Run Now" exercises its real internal endpoint end to end,
rather than requiring a mock.

While driving this workflow through the browser, a real trusted pointer click
occasionally hangs the renderer indefinitely (high CPU, no JavaScript-visible cause:
no render loop, no CSS animation, no `ResizeObserver`, no `focus()` loop) immediately
after certain state-changing interactions. It reproduces identically in two unrelated
browser-automation stacks and persists with Playwright's own trace recording disabled
and on the latest Radix UI releases, pointing to a browser/environment-level input
dispatch issue rather than application code. The new test avoids the affected
interactions by driving state transitions (enable, run, duplicate, delete) through the
same real HTTP endpoints the UI itself calls, and only observes resulting UI state via
page loads/reloads and one plain form-button click, which are unaffected.
